| --- | --- | --- | --- |
| POST | `/api/search/parse` | `{prompt: string}`; trimmed, 1–4000 characters | `{intent, destinations: [{targetId, resolution}], parser: "gemini" or "fallback", notice?}` |

Draft intent extensions preserve required single `mode`; optional `alternativeModes` contains additional distinct modes and excludes the primary mode. `numericExtreme` is one object `{field, direction: "min" or "max", percentage, minimumCount?, targetId?}`. Fields are `rent`, `bedrooms`, `bathrooms`, `sizeSqft`, `buildingAge`, `travel`; percentage is `(0,100]`, minimum count defaults to 10. Travel requires an existing target ID; scalar fields prohibit it. Numeric selectors do not accept arrays. `buildingAge` selects age in years, not build year; engine implementation must account for that direction. Unstated criteria stay absent.

`AreaFilter` was undefined in the root: the draft accepts `{kind: "neighbourhood" or "ward", id}` or `{kind: "near", point: {lng,lat}, radiusM}`. Safety's draft application payload is `{areaId, rate: number|null, relativeRate: number|null, byType: Record<string, number|null>, years: number[], caveats: Caveat[]}` with at least one caveat. These are application contracts awaiting owner alignment, never database definitions. The draft travel row uses camelCase `{listingId,targetId,mode,minutes,distanceM,poiId,computedAt,method}` and does not redefine D's SQL columns/cache keys. `straight_line` requires null minutes; `otp` requires numeric minutes.

Destination resolution uses `{status:"resolved",query,destination:{id,label,resolved}}`, `{status:"ambiguous",query,choices:[...]}` (at least two), or `{status:"unavailable",query,reason}`. Coordinates include source (`known_place`, `address_points`, `maptiler`); a true `representativePoint` requires its own label.

Completed search is `{status:"completed",results:[{id,listing,valuation,travel,safety,matchScore}],eligibleCount,notices}`. Pending is `{status:"pending",jobToken,pollUrl,expiresAt}` with matching token/path. Unavailable is `{status:"unavailable",reason:"timeout"|"routing_incomplete"|"capacity",message}`; it carries no partial exact results. The API runtime dispatches ordinary/scalar selection synchronously and exact travel selection to bounded in-memory jobs.

All request bodies use Zod. Shared error envelope is `{ "error": { "code": "…", "message": "…", "issues": [], "retryAfterSeconds": 1 } }`, where issues and retry delay are optional; each draft issue has `{path: (string|number)[], message: string}`. Root conventions require HTTP 422 validation errors and HTTP 429 plus `Retry-After` on limits; every route uses B's `jsonRoute({ name, body, rateLimit }, handler)`. Default unavailable listing services return 503; unknown listing UUID returns 404; expired, consumed or restarted jobs return 410. Domain unavailable search outcomes return HTTP 200. ## Draft API runtime — verified locally

`lib/api/runtime.ts` exports `createRuntime(options)` for isolated tests and `getRuntime()` for route composition. `getRuntime` stores one runtime on `globalThis`, so separate Next route bundles in one Node process share caches, quotas and jobs. Separate server processes/instances do not share state. Polling needs instance affinity until the team approves a different contract; a different/restarted process returns 410. No job, prompt or response is written to disk or logged by these modules.

Set server `SEARCH_FIXTURES=1` explicitly for eight synthetic listings and existing synthetic valuation/safety contexts; ordinary ad hoc targets receive calculated, labelled straight-line distance, never invented minutes. Fixture mode does not provide a router: exact travel jobs complete with `routing_incomplete`. Without fixture mode or injected owner adapters, listing search/detail return 503; parsing and known-place resolution still work. AI uses existing `AI_PROVIDER`, `GEMINI_API_KEY`, `GEMINI_MODEL`/`GEMINI_MODEL_FAST`; server MapTiler lookup reads the root team's `NEXT_PUBLIC_MAPTILER_KEY`. Injected dependencies/identity are composition hooks for owner integration and tests, not user request options. Fixture areas/indicators are synthetic; building data is unavailable and excluded rather than fabricated. Live detail awaits owner contracts.

Detail receives the same SearchIntent in query parameter `intent`, with `rawPrompt: ""`, `fieldSources: {}` and `droppedRequests: []` required to keep original prompt/source phrases out of URLs. It validates the full remaining intent and rescores the requested listing, even if that listing fails a hard filter or would not be selected by a percentile. Single-listing ad hoc routing shares `routeCandidateContexts` with ordinary search, retaining the three-second deadline, validation, owner-failure fallback and original intent scoring. Stale/removed/duplicate listings remain available to detail with status intact; detail returns duplicate listings present in the injected pool. Routed times can change between separate calls; live UI must reflect that limitation. URL context includes search criteria/destinations; hosting should avoid logging query strings. This implementation has no request logging. Unknown query keys and duplicate required query values are rejected. Detail lookup is a UUID; query context and token paths are validated before lookup. `hideUnconfirmed` is a result-selection option, not part of detail scoring.
