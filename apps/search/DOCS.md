# Natural-language rental search

## Distance-based travel estimates

An explicit request such as `within 10 minutes of Allan Gardens` creates a hard ten-minute limit. Without a stated mode, bounded proximity requests use walking. The basic parser recognizes arbitrary `minutes to/of/from` destinations; the Gemini guard rejects a softened, widened, omitted or mode-changed limit. Listings exceeding that mode's estimated limit are excluded, not just ranked lower.

Travel time is a planning estimate: `ceil(overheadMinutes + 60 * (straightLineMetres / 1000) * routeFactor / speedKmh)`. Zero distance returns zero minutes. Shared constants in `packages/shared/engine/config.ts` are heuristic assumptions, not calibrated routing or traffic data:

| Mode | Speed (km/h) | Route factor | Overhead (minutes) |
| --- | --- | --- | --- |
| Walk | 4.8 | 1.25 | 0 |
| Bike | 15 | 1.25 | 1 |
| Drive | 25 | 1.35 | 3 |
| Transit | 18 | 1.4 | 8 |

`estimateTravelMinutes` and `targetDistanceM` in the shared travel engine supply result cards, all four detail modes, hard time limits, scoring and travel ordering/percentiles. Resolved places use the listing and destination coordinates even without travel rows; amenities use the nearest measured POI distance. Times are labelled estimates and omit live traffic, schedules, weather and closures. The web runtime uses distance queries without attaching an OTP router. Raw distance rows retain `minutes:null` and `method:straight_line`; estimated durations are derived from them, never labelled as routed. Missing destination coordinates/POI data remain explicitly unavailable rather than generating a fabricated time. Carbon calculations still require their original routed-distance evidence.

## Gemini place normalization (2026-10-17)

`TravelTarget` accepts optional `normalizedQuery` (1–500 trimmed characters) for places with an original `query`. Gemini is instructed to recognize arbitrary named landmarks, businesses, streets and intersections, and may expand abbreviations or correct spelling into that search hint. For example, `query:"ROM"` retains the renter's exact words and source evidence while `normalizedQuery:"Royal Ontario Museum"` supplies the geocoding phrase. Invented queries without original prompt evidence are rejected; model-supplied coordinates are always discarded. This does not expand the basic parser's vocabulary when Gemini is unavailable.

Resolver cache keys include both names. ## P5.5b route states (2026-10-17)

`POST /api/listings/search` returns HTTP 200 `status:"completed",results:[],eligibleCount:0` for no matches; `eligibleCount` may be greater than zero when the result window is empty. The UI can show its existing empty state without treating this as a failure. An exact travel percentile returns HTTP 200 `status:"pending"` with an opaque token, `pollUrl` and expiry; `GET` on that URL repeats pending until it returns a terminal completed or unavailable response. Terminal `status:"unavailable"` reasons are `timeout`, `routing_incomplete` and `capacity`, mapped by A to `search_timeout`, `search_routing_incomplete` and `search_capacity`. No partial exact result is shown. Synchronous routes have no separate loading payload; the client displays loading while its request is in flight.

Handled HTTP failures in B routes use `{error:{code,message,issues?,retryAfterSeconds?}}`. Stable codes are `validation_error` (422), `rate_limited` (429 with `Retry-After`), `listing_not_found` or `area_not_found` (404), `search_job_expired` (410), `service_unavailable` (503), and sanitized `internal_error` (500). A already translates the search-relevant codes; unknown route codes fall back to its default error copy. Briefing data read failures now return 503 `service_unavailable` rather than a generic 500. The briefing's HTTP 200 `status:"insufficient_data"` is an honest content state when owner indicators are absent.

## Draft API runtime — verified locally

`lib/api/runtime.ts` exports `createRuntime(options)` for isolated tests and `getRuntime()` for route composition. `getRuntime` stores one runtime on `globalThis`, so separate Next route bundles in one Node process share caches, quotas and jobs. Separate server processes/instances share eligible parse interpretations through ai_cache; jobs, quotas and other memory caches remain per process. Polling needs instance affinity until the team approves a different contract; a different/restarted process returns 410. No job or raw prompt is persisted or logged; only privacy-reduced parse interpretations can enter ai_cache.

Set server `SEARCH_FIXTURES=1` explicitly for eight synthetic listings and existing synthetic valuation/safety contexts; ordinary ad hoc targets receive calculated, labelled straight-line distance, never invented minutes. Fixture mode does not provide a router: exact travel jobs complete with `routing_incomplete`. Without fixture mode or injected owner adapters, listing search/detail return 503; parsing and known-place resolution still work. AI uses existing `AI_PROVIDER`, `GEMINI_API_KEY`, `GEMINI_MODEL`/`GEMINI_MODEL_FAST`; server MapTiler lookup reads the root team's `NEXT_PUBLIC_MAPTILER_KEY`. Injected dependencies/identity are composition hooks for owner integration and tests, not user request options. Fixture areas/indicators are synthetic; building data is unavailable and excluded rather than fabricated. Live detail awaits owner contracts.

Detail receives the same SearchIntent in query parameter `intent`, with `rawPrompt: ""`, `fieldSources: {}` and `droppedRequests: []` required to keep original prompt/source phrases out of URLs. It validates the full remaining intent and rescores the requested listing, even if that listing fails a hard filter or would not be selected by a percentile. Single-listing ad hoc routing shares `routeCandidateContexts` with ordinary search, retaining the three-second deadline, validation, owner-failure fallback and original intent scoring. Stale/removed/duplicate listings remain available to detail with status intact; detail returns duplicate listings present in the injected pool. Routed times can change between separate calls; live UI must reflect that limitation. URL context includes search criteria/destinations; hosting should avoid logging query strings. This implementation has no request logging. Unknown query keys and duplicate required query values are rejected. Detail lookup is a UUID; query context and token paths are validated before lookup. `hideUnconfirmed` is a result-selection option, not part of detail scoring.
